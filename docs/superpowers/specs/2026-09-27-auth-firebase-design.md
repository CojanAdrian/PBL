# Auth & Firebase Groundwork — Design Spec

**Owner:** Adrian
**Date:** 2026-09-27
**Status:** Approved for planning

## Context

RoadFix (civic issue-reporting SwiftUI app) currently has no login/signup and no
Firebase integration in this repo — the checkout at `RoadFix/` still contains only
the default Xcode template (`ContentView.swift`, `RoadFixApp.swift`). Teammates'
files described in the team's status email (`MapView.swift`, `NewReportView.swift`,
`LocationManager.swift`, `ReportDetailView.swift`, `StaffDashboardView.swift`,
`Report.swift`, `ReportService.swift`) are not yet present in this repo/branch and
are assumed to land later via merge — this spec does not recreate them.

The team's DAS report already commits to Firebase Auth + Firestore, citing TLS
transport for "encryption in transit." Adrian's RBAC section flags, as the #1
October priority, that `StaffDashboardView` is currently only hidden by UI/tab
separation with no real access control behind it. This spec is the auth +
database groundwork that gives that RBAC gap a real, enforceable hook.

## Goals

- Real user accounts (Firebase Auth, email/password) for citizens and staff.
- A `role` per user, stored server-side in Firestore, not just in the client.
- A signup-time gate (invite code) so staff role isn't self-assignable by
  anyone who opens the signup screen.
- A baseline Firestore security-rules file that enforces the role server-side
  (closing the RBAC gap), even though wiring the existing report views to it
  is out of scope here (teammates' `ReportService.swift` work).
- Clean SwiftUI login/signup screens with client-side validation and mapped
  error messages, following the same "client-side gate as a first line of
  defense" pattern already used in `NewReportView.swift` per the email.

## Non-goals

- Rebuilding or stubbing teammates' views (MapView, StaffDashboardView, etc.).
  `ContentView` gets a minimal temporary post-login placeholder only.
- Location fuzzing, upvotes, photo upload — unrelated to auth.
- Deploying/publishing the Firestore rules for the user (done manually by
  Adrian in the Firebase console, steps included below).
- Password reset / email verification flows (documented as a deferred item).

## Architecture

New files under `RoadFix/`, following the existing flat layout:

```
RoadFix/
  RoadFixApp.swift          (edited: FirebaseApp.configure() on launch)
  RootView.swift            (new: switches Auth screens <-> signed-in app)
  ContentView.swift         (edited: temporary post-login placeholder body)
  Auth/
    AuthViewModel.swift     (new)
    LoginView.swift         (new)
    SignUpView.swift        (new)
  Models/
    AppUser.swift           (new)
  GoogleService-Info.plist  (added manually via Xcode, not generated by Claude)
firestore.rules             (new, at repo root — pasted into console manually)
```

`AuthViewModel` (`ObservableObject`) is the single seam:
- `@Published var currentUser: AppUser?`
- `@Published var isLoading: Bool` (true only during the initial auth-state check)
- `@Published var errorMessage: String?`
- `func signIn(email: String, password: String)`
- `func signUp(email: String, password: String, staffCode: String?)`
- `func signOut()`

It registers a Firebase `addStateDidChangeListener` (not just a one-time check)
so external sign-outs/expired sessions are reflected live.

`RootView` holds `AuthViewModel` as `@StateObject` and switches:
- `isLoading == true` → `ProgressView()`
- `currentUser == nil` → `LoginView`
- else → `ContentView` (today's placeholder; teammates' real tab view drops
  in here later without touching the auth layer)

## Data model (Firestore)

```
users/{uid}
  email: string
  role: "citizen" | "staff"
  createdAt: timestamp

config/staffInviteCode        (single doc)
  code: string
```

Signup flow:
1. `Auth.auth().createUser(withEmail:password:)`
2. If a non-empty `staffCode` was supplied, read `config/staffInviteCode` and
   compare. Match → `role = "staff"`. No code, or wrong code → `role =
   "citizen"` (signup still succeeds; we never reveal whether a code was
   close/wrong, just that it wasn't accepted).
3. Write `users/{uid}` with `email`, `role`, `createdAt`.
4. If step 3 fails after step 1 succeeded, surface a clear error and leave the
   user signed out (delete the partially-created auth user via
   `user.delete()` so retry doesn't hit "email already in use").

`AppUser` is a plain struct (`uid`, `email`, `role`) decoded from the
`users/{uid}` doc right after sign-in.

### Firestore security rules (baseline)

Provided as `firestore.rules` in this repo for Adrian to paste into the
Firebase console manually (not deployed by Claude). Enforces:
- A user can read/write only their own `users/{uid}` doc, and cannot set
  `role` to anything on update (role is set once at creation via the signup
  flow's server-trusted write — see note below — and is otherwise read-only
  from the client).
- Any authenticated user can read `reports/{reportId}` docs, and can create
  one, but only as themselves (`reporterId == request.auth.uid`) and only
  with the initial `status == "reported"` — a citizen cannot set an
  arbitrary status (e.g. `"resolved"`) at creation time.
- Only a doc whose `users/{request.auth.uid}.role == "staff"` can write to a
  report's `status` field on update; a non-staff user can otherwise only
  update their own report (`reporterId == request.auth.uid`).
- `config/staffInviteCode` is readable by any authenticated user (needed for
  the signup-time comparison) and not writable by clients at all.

Note: because the role write happens directly from the client during signup
(no Cloud Function/server), a technically sophisticated user could still call
`users/{uid}.set({role: "staff"})` directly at signup time before the rule
"role is read-only after creation" kicks in, if the invite-code check were
skipped client-side. This is a known limitation of doing invite-code
validation client-side rather than in a Cloud Function — documented below as
a deferred hardening item, consistent with the DAS report's existing pattern
of flagging what's deferred to Oct–Dec.

## Screens

**LoginView**
- Email + password fields.
- "Log In" button, disabled until both fields non-empty.
- Inline error text from `AuthViewModel.errorMessage`.
- Link to `SignUpView`.

**SignUpView**
- Email, password, confirm-password fields.
- Collapsible "I'm staff" disclosure revealing a staff-code field.
- "Create Account" button, disabled until: email contains "@" and ".", password
  ≥ 6 characters (Firebase's own minimum), password == confirm.
- Inline error text from `AuthViewModel.errorMessage`.

**Error mapping**: a `mapAuthError(_ error: Error) -> String` helper switches
on `AuthErrorCode` (wrongPassword, userNotFound, emailAlreadyInUse,
networkError, weakPassword, invalidEmail, etc.) to plain user-facing copy,
falling back to a generic "Something went wrong, try again" for anything
unmapped — never surfaces raw `NSError` text. `wrongPassword`,
`invalidCredential`, and `userNotFound` all map to the *same* message
("Incorrect email or password.") rather than distinct ones — a login form
that says "no such account" vs. "wrong password" as different messages lets
an attacker enumerate which emails have accounts, which defeats the point of
having error messages at all on this screen.

**ContentView (temporary placeholder)**: "Signed in as `{email}` (`{role}`)"
text + "Sign Out" button, marked with `// TODO:` for whoever merges in the
real tab view.

## Testing plan (manual, no test target exists yet)

- Empty-field submission on both screens → button stays disabled.
- Sign up with a new email/password → lands on placeholder ContentView,
  Firestore shows `users/{uid}` with `role: "citizen"`.
- Sign up with the correct staff code → `role: "staff"` in Firestore.
- Sign up with a wrong staff code → succeeds as `role: "citizen"` (silent
  fallback, no error).
- Duplicate signup (same email twice) → mapped "email already in use" error.
- Wrong password on login → mapped "incorrect password" error, no account
  lockout info leaked.
- Sign out → relaunch app → lands back on LoginView, not signed in.
- Kill app mid-session (already signed in) → relaunch → skips LoginView
  (session persisted by Firebase Auth SDK by default).

## Manual setup steps (Adrian, before this code will build/run)

1. console.firebase.google.com → Add project (e.g. "RoadFix"); Analytics off.
2. Authentication → Get started → enable **Email/Password** provider.
3. Firestore Database → Create database → start in **test mode**.
4. In Firestore, manually create `config/staffInviteCode` doc with a `code`
   string field (e.g. `ROADFIX-STAFF-2026`) — share this code out-of-band with
   whoever should get staff accounts (Adrian, teammates for testing).
5. Project settings → Your apps → Add app → iOS. Bundle ID must exactly match
   the Xcode target's Bundle Identifier.
6. Download `GoogleService-Info.plist`, drag into `RoadFix/` in Xcode (Copy
   items if needed; add to RoadFix target).
7. Xcode → File → Add Package Dependencies →
   `https://github.com/firebase/firebase-ios-sdk` → add **FirebaseAuth** and
   **FirebaseFirestore** to the RoadFix target.
8. Once teammates' rules are ready to enforce for real, paste
   `firestore.rules` into Firestore Database → Rules tab → Publish (switches
   off test mode).

## Deferred / out of scope (for the DAS report's Oct–Dec log)

- Invite-code check happens client-side, not in a Cloud Function — a
  determined user could bypass it by writing to Firestore directly with a
  captured auth token. Real hardening needs a Cloud Function or App Check.
- No password reset / forgot-password flow.
- No email verification requirement before use.
- Firestore rules here already validate `reporterId == request.auth.uid` and
  a fixed initial `status == "reported"` on report creation, and restrict
  non-staff updates to the reporter's own doc without touching `status` — but
  they're written against assumed field names/values (`reporterId`, `status`,
  the literal `"reported"`) since `Report.swift` doesn't exist in this repo
  yet. Re-verify these once `Report.swift`/`ReportService.swift` land, in
  case the real field names or initial-status value differ.
- Test-mode Firestore must be switched to real rules before the app is
  anything more than an internal demo — test mode allows any read/write to
  anyone.
